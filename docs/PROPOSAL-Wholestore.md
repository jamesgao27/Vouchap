# Proposal：Wholestore

**面向厂家与经销商的 B2B 下单、履约与结算平台**  
**状态**：内部讨论草案（不实施代码）  
**日期**：2026-08-15  
**依据**：2026-08-11 中文极简计划书 + 产品架构约束（独立用户/Space、Factory↔Dealer）

产品面向用户的文案使用 **English**（Factory / Dealer / Invoice 等）。本文为内部讨论，使用中文。

---

## 0. 一句话

经销商在 **Wholestore 门户**注册、看专属价、下单、查账单；厂家在后台审核客户、管价格与订单；**Finale Inventory** 管库存与履约；**QuickBooks Online** 管发票、应收与总账。目标是减少人工下单和对账，保证库存、订单、财务三套数据一致。

**建议周期**：集成验证 2–3 周 → MVP 累计 **12–16 周** → 完整版累计 **20–28 周**。  
**建议团队**：产品/业务 1、设计 0.5、开发 3–4、测试 0.5–1，财务负责人参与会计映射与验收。

---

## 1. 目标与非目标

### 1.1 要解决的问题

- 经销商靠邮件/表格下单，错单、漏单、价格不一致。  
- 库存在仓库系统、订单在表格、账在会计软件，三套对不上。  
- 厂家无法标准化入驻审核、客户价、账期与催款。

### 1.2 非目标（完整版之前不做）

- 自动信用审批、多级采购审批、复杂催款工作流  
- 退货与 Credit Memo、EDI、多币种  
- **多厂家共用的平台型市场**（MVP 按「一个厂家 + 多家经销商」）  
- QuickBooks Desktop  
- 门户、Finale、QBO 三方各自开票/收款（禁止重复入账）

---

## 2. 角色与租户

| 产品文案 | 组织 | 说明 |
|---|---|---|
| Factory | 厂家 Space | 审核经销商、配置价格与授信、监控订单与对账 |
| Dealer | 经销商 Space | 企业入驻、内部采购员、下单与查账 |
| Member / Admin | Space 成员 | 每个 Space 多名用户；厂家与经销商各自有角色权限 |

约束：

- 用户与 Space **只属于 Wholestore**，与其它应用账号不通。  
- 经销商入驻需厂家人工审核后才启用下单。  
- 经销商内部可管采购人员与权限（谁能下单、额度上限在完整版强化）。

## 3. 三个系统的分工（架构核心）

```
经销商 Web/App          厂家后台
        \                /
         \              /
          Wholestore 门户
     （身份、入驻、价格展示、购物车、
       下单编排、审批、账单展示、审计）
                |
        +-------+--------+
        |                |
 Finale Inventory     QuickBooks Online
 商品/SKU/包装        Invoice / AR
 仓库库存/预留        Payment / COGS
 销售订单/发货        库存资产 / 总账
```

| 系统 | 系统中的「事实来源」 | 门户做什么 |
|---|---|---|
| **Wholestore 门户** | 用户、入驻审核、客户价与账期政策、购物车、门户订单草稿、审批记录、操作日志 | 编排流程；**不**作为库存账本，**不**作为总账 |
| **Finale Inventory** | 商品/SKU、包装规格、仓库库存、库存预留、销售订单、发货与履约状态 | 读目录与库存；下单后写销售订单；回写状态 |
| **QuickBooks Online** | Invoice、应收账款、付款、COGS、库存资产、总账 | 展示 Invoice/余额；按约定路径触发或读取 Payment |

**硬原则（会计一致性）**

> 同一笔 Invoice、Payment 或会计分录，只能由 **一条确定的流程** 创建。  
> 门户、Finale、QBO 不得各写一笔。集成层必须带幂等键（订单号 / Invoice 号 / Payment 号），失败只重试同一条，禁止补偿时再插一笔。

建议默认（启动前仍须书面确认，见第 8 节）：

| 对象 | 建议归属 |
|---|---|
| SKU / 库存 / 履约 | Finale |
| 客户专属价、阶梯价、MOQ、整箱规则、授信展示策略 | 门户（Finale 无完整 B2B 价盘时） |
| Invoice | 由履约/开票链路 **只走一条**：Finale→QBO 或 门户触发 QBO，禁止两条都开 |
| Payment | **只由一个系统**写入 QBO（支付网关回调→门户编排→QBO，或 QBO 收付款后回写门户） |

## 4. 功能架构

门户按 **八个能力域** 划分。域之间通过「门户订单」这一根单据串联；库存与财务不在门户落账。

### 4.1 能力域与主流程

```
[1 入驻与账号] → 审核通过
        ↓
[2 商品与价格] ← 同步 Finale 目录/库存
        ↓
[3 选品与下单] → 门户订单（含客户 PO#）
        ↓
[4 订单与物流] → 写入 Finale → 预留/发货/跟踪
        ↓
[5 支付与账期] → 只读或按规则触发 QBO Invoice/Payment
        ↑
[6 厂家后台] 审核、价盘、授信、监控、对账
[7 权限与审计] 贯穿全程
[8 集成与运维] 同步、重试、去重、告警、人工修复
```

### 4.2 八域说明

**1. 经销商入驻与账号**  
企业注册、资质文件、厂家审核、启用/停用；经销商 Space 内采购员邀请与基础角色（Admin / Buyer）。

**2. 商品与价格**  
从 Finale 同步商品、SKU、规格、可售库存；门户维护客户价、阶梯价、MOQ、整箱/散件。展示价 = 该经销商价盘 ∩ 可售 SKU。

**3. 选品与下单**  
搜索、购物车、确认页、客户采购单号。MVP 含历史订单再下（复制）。订单模板、快速补货放完整版优先队列的前段。

**4. 订单与物流**  
门户订单提交后 **幂等写入 Finale**；回传订单状态、发货状态。MVP：整单状态 + 发货状态展示。部分发货/缺货：Finale 有数据则只读展示；复杂异常处理放完整版。

**5. 支付与账期**  
MVP：账期客户（Net 15/30/60）看信用额度（可先手工维护）、待付、Invoice 列表与 PDF/链接。在线支付可放 MVP 末或完整版，但必须先锁定「谁写 QBO Payment」。

**6. 厂家管理后台**  
经销商审核队列、客户档案、价盘配置、订单监控、同步失败队列。授信配置 MVP 可手工；催款/对账工作台放完整版。

**7. 权限与审计**  
厂家与经销商基础角色；关键操作写审计日志（审核、改价、下单、重试入账）。采购额度与多级审批放完整版。

**8. 集成与运维**  
作业：目录同步、库存同步、下单推送、履约回写、Invoice 同步。每条外部写操作带 idempotency key；死信队列 + 告警 + 人工「仅重试、不新建」。

### 4.3 MVP vs 完整版

| 能力 | MVP（12–16 周累计） | 完整版（20–28 周累计） |
|---|---|---|
| 入驻 + 人工审核 + 启用 | 必须 | — |
| 经销商内部成员 | 基础 Admin/Buyer | 细粒度权限、采购额度 |
| Finale 商品/库存同步 | 必须 | 多仓、更实时 |
| 客户价 / 阶梯 / MOQ / 整箱 | 必须（规则可先简化：客户价 + MOQ） | 完整阶梯与包装规则 |
| 购物车 + 下单 + PO# | 必须 | 模板、快速补货 |
| 写入 Finale + 状态回写 | 必须 | 缺货策略、部分发货异常流 |
| Invoice 查看 | 必须（只读 QBO） | 收据、对账、催款 |
| 在线支付 | 可选（建议完整版，除非付款归属已锁定） | 必须（若业务需要） |
| 厂家后台 | 审核、档案、价盘、订单、失败队列 | 授信自动化、催款、分析 |
| 审计日志 | 必须（关键写操作） | 敏感操作完整集 |
| 退货 / Credit Memo / EDI / 多币种 / 多厂家 | 不做 | 按优先级选做 |

### 4.4 端形态

| 端 | MVP | 完整版 |
|---|---|---|
| **Web 门户**（经销商 + 厂家后台） | 主路径，必须 | 持续 |
| **移动端 App** | 不堵 MVP 主路径；若并行，见成本「加项」 | 查单、补货、审批通知 |

B2B 下单与价盘适合大屏；手机以查询与催办为主。

### 4.5 软件分层（实现视角）

```
apps/wholestore          Web +（可选）iOS/Android 壳
wholestore-domain        价盘、购物车、门户订单、入驻单、集成编排
集成适配器               Finale API / QBO API / 支付网关
身份与组织               用户、Space、成员、邀请、Factory↔Dealer 关系
数据                     Wholestore 库（业务）+ 外部系统（库存账/总账）
```

门户订单是内部主键；Finale 销售订单号、QBO Invoice 号作为外部引用，一对一映射表防重复。

## 5. 主数据流（验收用）

集成验证与 MVP 共用同一条黄金路径：

1. Finale 有 SKU 与库存 → 门户可同步并展示。  
2. 经销商入驻 → 厂家审核通过 → 挂上客户价。  
3. 购物车提交 → 生成门户订单（幂等键）→ **只创建一次** Finale 销售订单并预留库存。  
4. 发货（Finale）→ 门户展示状态。  
5. **只创建一次** QBO Invoice（路径在启动前锁定）。  
6. 若有付款： **只创建一次** QBO Payment，门户展示已付/余额。  
7. 人为重复点击提交 / 作业重试，不得产生第二张订单或第二张发票。

## 6. 实施阶段与工期

以下按 **日历周、可并行** 估算。MVP 累计从第 1 周起算。

### 6.1 阶段总览

| 阶段 | 日历周 | 累计 | 主要结果 |
|---|---|---|---|
| **S0 启动拍板** | 并行于 S1 前 3–5 天 | — | 第 8 节五项书面确认 |
| **S1 集成验证** | **2–3 周** | 2–3 | 受控真实数据跑通：读商品库存 → Finale 测试单 → 发货 → QBO 财务结果 → 付款验证 |
| **S2 MVP 开发** | 10–13 周 | **12–16** | 入驻、客户价、购物车、下单写 Finale、状态、Invoice 只读、基础后台、告警 |
| **S3 完整版** | 8–12 周 | **20–28** | 授信、采购审批、催款、退货/Credit Memo、复杂异常、基础分析（按切分） |

**S1 必须先做。** 未跑通 Finale 写单与 QBO 入账前，不锁定最终预算，不排满 S2 人月。

### 6.2 S2（MVP）内部切片（示例 14 周中位）

| 周 | 焦点 |
|---|---|
| 1–3 | S1：API 权限、沙箱、黄金路径、会计科目映射草案 |
| 3–5 | 入驻、审核、Space 成员、基础权限、文件上传 |
| 4–7 | 目录/库存同步、客户价盘、商品列表与搜索 |
| 7–10 | 购物车、下单、幂等写 Finale、状态回写 |
| 10–12 | 厂家后台监控、失败队列、Invoice 只读、审计日志 |
| 12–14 | 端到端联调、权限回归、告警、UAT（含财务） |
| 15–16 | 缓冲：部分发货只读、支付若已拍板则最小闭环，否则冻结 |

S1 与入驻可部分重叠，但 **写 Finale / 写 QBO 的适配器** 以 S1 结论为准，避免返工。

### 6.3 工期风险（已计入 12–16 而非 10 周的原因）

- Finale/QBO API 权限、沙箱与生产行为不一致  
- 客户价与包装规则比预期复杂  
- 财务要求改 Invoice 生成时点（发货开票 vs 下单开票）  
- 部分发货被临时升为「必须可操作」而非只读  

每发生一项未拍板变更，按 **+2–4 周** 计。

## 7. 团队、工作量与成本

### 7.1 建议编制（与计划书一致）

| 角色 | FTE | 职责 |
|---|---|---|
| 产品/业务 | 1.0 | 入驻规则、价盘、订单状态机、与财务对齐 |
| 设计 | 0.5 | Web 门户与后台；移动若做则再加 |
| 开发 | 3–4 | 门户、集成、后台；建议 1 人主攻 Finale+QBO |
| 测试 | 0.5–1 | 下单幂等、账务一致性、权限 |
| 财务负责人 | 顾问 | 科目映射、Invoice/Payment 路径验收，非全职 |

中位编制按 **开发 3.5、测试 0.75** 计。

### 7.2 工作量（人周）

1 人周 = 1 人 × 5 个工作日。不含厂家 IT 开通 API 的等待（应在 S1 前完成）。

| 范围 | 产品 | 设计 | 开发 | 测试 | **合计人周** | 约人月 |
|---|---|---|---|---|---|---|
| **S1 集成验证**（3 周） | 1.5 | 0.3 | 9–12 | 1.5 | **12–15** | 3–4 |
| **MVP 累计**（14 周中位） | 14 | 7 | 49 | 10 | **约 80** | **约 20** |
| **MVP 累计**（16 周上限） | 16 | 8 | 56 | 12 | **约 92** | **约 23** |
| **完整版累计**（24 周中位） | 24 | 12 | 84 | 18 | **约 138** | **约 35** |
| **完整版累计**（28 周上限） | 28 | 14 | 98 | 22 | **约 162** | **约 41** |

完整版人周含 MVP，不是增量另算。若只算 S3 增量（约 8–12 周）：大约 **+45–70 人周**。

**移动端 App（加项，未计入上表）**  
查询/下单精简版约 **+16–24 人周**（约 +4–6 日历周，需多 1 名客户端或从 Web 抽人，会拉长 MVP 或放到 S3）。

### 7.3 成本口径（必须先选一种）

成本随雇佣地变化大，**人周是稳定量，金额是情景**。以下为 **人力成本**，不含 Finale/QBO/支付的软件订阅、短信、对象存储。

**情景 A｜北美合同制（综合约 USD 120–160 / 人时）**  
按 40 小时/人周、中位 $140/时：

| 范围 | 人周中位 | 约 USD |
|---|---|---|
| S1 | 14 | **8–10 万** |
| MVP | 80 | **40–50 万** |
| 完整版累计 | 138 | **70–90 万** |

**情景 B｜混合（本地产品+财务，研发在成本较低地区，综合约 USD 45–75 / 人时）**  
中位 $60/时：

| 范围 | 约 USD |
|---|---|
| S1 | **3–4 万** |
| MVP | **18–25 万** |
| 完整版累计 | **30–45 万** |

**情景 C｜自有团队完全成本（薪酬+福利+管理，示意 USD 1.2–1.8 万 / 人月）**

| 范围 | 人月中位 | 约 USD |
|---|---|---|
| MVP | 20 | **24–36 万** |
| 完整版累计 | 35 | **42–63 万** |

人民币可按当时汇率换算；立项时用 **人周 × 选定人时单价** 锁定预算，不要只锁「16 周」。

### 7.4 其它直接成本（量级）

| 项 | 量级（年，示意） |
|---|---|
| Finale、QBO、支付网关订阅 | 以厂家现有合同为准（门户不替代） |
| 云主机 / 数据库 / 文件存储 / 监控 | MVP 年约 USD 2–8 千 |
| 域名、证书、邮件 | 低 |
| 意外：QBO 会计实施顾问（若科目未就绪） | 一次性 USD 5–15 千 |

### 7.5 成本怎么控

1. **先花 S1 的 12–15 人周**：证明写单与入账路径，再批 MVP 全预算。  
2. MVP **砍掉**：在线支付、多级审批、退货、移动 App、复杂阶梯（可先「每客户一口价 + MOQ」）。  
3. Invoice/Payment **单一写入者** 写进合同级说明，避免 S2 中途改会计路径（典型返工 3–6 周）。  
4. 多厂家平台不要进 MVP，否则租户模型与价盘工作量接近再做一个产品。

## 8. 启动前必须书面确定

| # | 事项 | 对工期/成本的影响 | 本提案用于报价的假设 |
|---|---|---|---|
| 1 | 一个厂家，还是多厂家平台 | 多厂家 ≈ 另做一套租户与权限，MVP +8–16 周 | **一个厂家** |
| 2 | QBO 还是 Desktop | Desktop 集成模式不同，不按本报价 | **QuickBooks Online** |
| 3 | 客户价与授信在门户还是 Finale | 决定价盘工作量和同步方向 | **价盘与授信策略在门户**；SKU 在 Finale |
| 4 | 谁创建正式 QBO Payment | 支付与对账的唯一入口 | **S1 验证后锁定一条链**；MVP 可先账期+只读 Invoice |
| 5 | 首期是否必须缺货、部分发货、退货、多级审批 | 每多一项硬需求 +2–4 周 | MVP：**状态只读**；退货与多级审批 **不做** |

未签字前，12–16 周与第 7 节金额均为 **假设 1+2+3+5 成立** 的中位值。

## 9. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 三系统重复入账 | 财务不可用 | 幂等键、单一写入者、对账抽样 |
| S1 失败或权限不足 | S2 无法开工 | 先做 S1，厂家 IT 预开通 |
| 价盘规则膨胀 | 工期翻倍 | MVP 一口价+MOQ |
| 开票时点争议（下单 vs 发货） | 返工 QBO 映射 | 财务在 S1 验收签字 |
| 把门户做成第二个库存账 | 与 Finale 双写 | 门户不存可用库存权威值 |
| 过早做移动端 | 稀释 Web MVP | 移动作加项 |

## 10. 建议决策与下一步

1. 立项 **Wholestore** 为厂家–经销商 B2B 门户，核心系统为 **门户 + Finale + QBO**。  
2. 批准 **S1 集成验证（2–3 周，约 12–15 人周）**，用受控真实数据跑通第 5 节黄金路径后再锁定 MVP 预算。  
3. MVP 按第 4.3 节「必须」列交付，日历 **累计 12–16 周**，人力约 **80–92 人周**；金额按第 7.3 节选定情景。  
4. 完整版不自动开工，按授信、审批、催款、退货的业务优先级切包。
